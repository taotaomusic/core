## 🔴 根因（2026-09-19，用户反馈「搜索结果和波点客户端不一样」）

**我们搜出来的根本不是第一页的歌 —— 上游 `pn` 是 0 基，我们按 1 基传了。**

上游 `search/music/list` 的偏移量是 **`offset = pn × rn`**，实测（关键词「周杰伦」，
「首条在真实结果序列中的位置」）：

| pn | rn | 位置 |
| --- | --- | --- |
| 0 | 20 / 40 / 60 | **第 0 位** |
| 1 | 20 | 第 20 位 |
| 1 | 40 | 第 40 位 |
| 1 | 60 | 第 60 位 |
| 2 | 20 | 第 40 位 |
| 3 | 20 | 第 60 位 |

参考实现 `server/bodian/index.ts` 写的是 `pn: page`，本项目照抄了 ——
于是 `page=1` 实际请求 `pn=1`，**拿到的是第二页的歌**。而客户端默认 `num=60`，
`rn=60` 又把偏移放大到 60，所以看到的是**第 61 首起**的歌。

**判据是波点 App 自己**（`blutter` 逆向产物 `C:\Users\kiwi\Desktop\blutter\out-bodian`）：

- 单曲页 `search_result_single_widget.dart` 发
  `{"pn": 0, "rn": max(已加载条数 + 20, 20), "keyword", "correct", "bdSearchApiv": 2}`
- 综合页 `search_result_default_widget.dart` 发
  `{"pn": 0, "rn": 40, "keyword", "correct", "bdSearchApiv": 6}`
  到 `search/comprehensive/v2/list`，且 `encrypt: true`
- **`pn` 恒为 0**，翻页靠 `rn` 增长（`field_43` 是已加载条数，首页前重置为 0）

**修复前后对照**（裁判 = App 综合页的 `musicpage`，即用户实际看到的列表）：

| 关键词 | 修复前（`pn=1&rn=60`） | 修复后（`pn=0`） |
| --- | --- | --- |
| 周杰伦 | 与裁判重合 **0 条** | **前 30 条逐条一致** |
| 七里香 | 与裁判重合 **0 条** | **前 7 条逐条一致** |
| 晴天 | 与裁判重合 **0 条** | 前 17/20 一致 |

（晴天差 3 条是因为综合页会插推广项；单曲接口本身是对的。）

### 修复的两处

1. **`bodian.client.ts`**：新增 `upstreamPage(page)` = `max(0, page - 1)`，
   所有 7 个搜索方法统一走它（`searchTips` 的硬编码 `pn: 1` 改成 `0`）。
2. **`kuwo.client.ts`**：上游页大小**固定 20**，不再把调用方的 `limit` 当 `rn`。
   两个理由：
   - `rn` 一变，同一个 `pn` 指向的位置就变 → 翻页出现空洞或重叠；
   - **`rn` 会参与排序**（上游先取 top-`rn` 再排）。实测「稻香」`rn=20` 与 `rn=60`
     从第 10 首起分叉；而 `rn=20` 与 `rn=40` 的前 20 首在 5 个关键词上完全一致 ——
     小窗口稳定。20 也是 App 的首页页大小。

   调用方要的条数（最多 60）改为**多取几个上游页再拼接**，与「过滤掉不可播的歌」正交。

**回归断言**（`verify-contract.mjs`，253 项基线里的 2 条）：

- 「同一页不同页大小返回同一批歌（起点不随 num 漂移）」——
  旧实现下 `num=20` → `pn=1,rn=20` → 偏移 20，`num=60` → `pn=1,rn=60` → 偏移 60，
  **必然失败**；这是不需要外部裁判就能守住这个 bug 的不变量。
- 「第 1 页与第 2 页不重叠（翻页必须前进）」。

### 顺带确认的两件事

- **另外两个音源没有这个问题**：腾讯 `page=0` 与 `page=1` 返回相同 → 1 基，我们传 `page=1` 正确；
  网易 `page=0` 直接报错 → 也是 1 基。（腾讯相邻页有 1 条上游抖动，属上游行为。）
- **`search/comprehensive/v2/list` 是通的，不需要加密**：普通 GET 即 `code=200`。
  `encrypt: true` 在 `http_utils.dart` 里的实际作用是**算 `sign` 并补 uid/token/timestamp 头**，
  不是加密请求体。目前没接入 —— 单曲接口已经能对齐，综合页多出来的是歌单/歌手/专辑等板块，
  本项目不需要。

### 后续修复：短信发码失败的报错曾完全误导

后台报 `{"code":5020,"message":"酷我没有接受这次验证码请求，请确认号码可用"}`。
直打上游复现为 `HTTP 200 {"code":200,"msg":"success"}` —— **参数名 `encvMobile` 与
XOR+base64 加密都是对的，号码也可用**，所以这句文案本身就是错的。

根因两层：

1. `sendSms()` 只返回 `boolean`，把上游业务码吞掉了。
2. `parseJson()` **只看 body、完全不看 `response.status`**，响应不是 JSON 时返回 `{}`，
   `Number(d?.code)` 变成 `NaN`。于是**被网关/WAF 拦成 403、上游 502、号码不可用、
   发码频率超限**全部被压成同一句话，把排查方向带偏。

修法：

- `bodian.client.ts` 新增 `signedGetMeta` / `signedPostMeta`（返回 `{status, data}`），
  原方法委托它们，既有调用方行为不变；新增哨兵常量 `UPSTREAM_UNPARSABLE = -1`。
- `sendSms` / `loginSms` 改用 meta 版并带上 HTTP 状态；`loginSms` 顺带修掉了
  「响应不可解析时报出 `酷我登录失败：NaN`」的同一个缺陷。
- `kuwo.client.ts` 新增 `describeUpstreamFailure()`：哨兵码直接透出说明，
  **不展示成「上游业务码 -1」**；其余格式化成 `上游业务码 11003：短信发送失败`。

现在的报错长这样：

```
酷我没有接受这次验证码请求 —— HTTP 403，响应体不是 JSON（多半被网关/WAF 拦截，或上游异常）
酷我没有接受这次验证码请求 —— 上游业务码 11003：短信发送失败
```

**2026-09-19 真实条件下的验证**：用真实号码发码时上游回了 `code=11002`，日志里原样透出
「**上游业务码 11002：发送短信达到频次限制**」。旧代码会把它压成「请确认号码可用」，
把排查方向带偏成「换个号试试」—— 这次一眼就能看出是频次限制。
（此前只有伪造响应的分支测试，这是第一次在真实上游响应上验证。）

验收：伪造上游响应跑通 403 / 502 / 业务码 / 成功 / `11004` 五个分支；
`tsc --noEmit` 干净；契约 **249 项全绿**，`Mapped` 路由 **113**；`dist/` 已重建。

> ⚠️ 仍未解决：**发码失败的真实原因还没确定**。本机直打上游两次都是 200，
> 说明参数没问题，差异只可能在服务器出口（数据中心 IP 被风控）或当时的发码频率限制。
> 这次修复的价值是**下次再失败时能直接看到是哪一种**。

`code` / `data.{duplicate,pn,resultList,rn,total}`，每条歌曲是 `album` / `artists` /
`audios` / `duration` / `id` / `payInfo` / `searchTag` / `videoType` 等**全是歌曲自身的属性**。
唯一理论上可能与权益相关的是 `payInfo.listen_fragment`（`"1"` = 只能试听片段），
但它是歌曲级标记（还带 `refrain_start` / `refrain_end` 片段边界），真实 VIP 账号拿到的值也相同。

**凭据到底在哪儿起作用 —— 逐环节实测（含真实 VIP 凭据）：**

| 环节 | 匿名 | uid=12345678 + 随机 token | 真实 VIP 账号 | uid=abc（非数字） |
| --- | --- | --- | --- | --- |
| 搜索 `search/music/list` | 正常 | **与匿名逐字段相同** | **与匿名逐字段相同** | 与匿名逐字段相同 |
| 单曲信息 `service/music/info` | 正常 | 与匿名相同 | **与匿名相同**（`audios` 也相同） | 与匿名相同 |
| 取址 `playbasic/music/v2/audioUrl` | **有** mp3 128k | 有 mp3 128k | **有** mp3 128k | **无** |

即：**`token` 的取值被彻底忽略；`uid` 只在取址环节被解析一次形状**（非数字就静默不下发地址）。
**除了「uid 写坏了会弄坏取址」这一条，账号对本服务可达的全部上游接口没有任何可观测影响。**

> ⚠️ **这推翻了「待决策」第 1 条的推翻理由。** 那条推翻匿名直连的依据是
> 「换账号结果就可能不同」+「实测确认登录与不登录拿到的内容不一样」，
> 但两轮对照（伪造 + 真实 VIP）**都没有复现出任何差异**。
> 结构性原因：**这个复刻版上游没有任何用户维度接口**（没有「我的收藏」「我的歌单」
> 「用户信息」），凭据根本没有能被消费的地方。

> ❗ **一个容易误判的点：后台「测试」通过 ≠ 凭据被上游识别。**
> `probeCredential` 请求 `mp3/320k` 并回报真实码率，而**匿名同样能取到地址、同样返回
> mp3 128k** —— 所以「测试通过」只证明了「这个账号能取到地址」，无法区分「凭据生效」
> 与「匿名也能用」。它唯一能区分的是 **token 是否为空**（为空会加「匿名」前缀）。
> 同理，**本服务也没有任何接口能验证 token 的有效性**，因为上游没有用户维度接口。

> ❗ **另一个必须分开验的轴：「上游不读」≠「我们没发」。**
> 两者的**症状完全一样**（都是「登录了没变化」），只看对照结果分不出来。
> 上面那些对照都是**手搓 `BodianClient` + `setCredentials`**，证明不了线上链路有没有把
> 凭据带出去。所以单独补了一个**端到端探针**：往验证库塞一条启用账号（合成 token，
> 不碰真实凭据），用**真实编译产物** `KuwoClient` 跑一次搜索，抓出站请求头。
>
> **结果：`uid` / `token` 两个头都在，且与库里的值逐字符相同。**
> 出站共 **12 个头**：`appid` / `api-ver` / `User-Agent` / `Accept` / `Origin` / `Referer` /
> `Content-Type` / `uid` / `token` / `ts` / `nc` / `sign`。
>
> **「多传了什么」的准确答案**：与参考实现 `server/bodian/index.ts` 的 `baseHeaders()`
> 逐字段比对，**只多传了 `sign` 一个头**（参考实现没算它）。而消融测试证明
> `sign` 同样不被校验。12 个头里上游**真正读取的只有 `Origin` 与 `Referer`** ——
> 缺任一个回 HTTP 402 且 `msg` 为空；其余 10 个（含 `uid`/`token`）逐个删掉，
> 响应**一个字节都不变**。
>
> 结论：**凭据链路是通的，值也传对了，上游就是不读。** 不存在「我们传丢了/传错了」这个可能。

**所以「修了个寂寞」这句判断是准确的，而且范围比搜索更广：**
- 「配了账号搜索没变化」**不是 bug，是上游行为**。把凭据接回**搜索**链路收益为零。
- `upsertByLogin` 的 `enabled` 修复**也不影响任何输出** —— 它只保证「账号状态被尊重」，
  但账号本身不改变任何结果。保留它的价值是「不让坏账号伪装成正常」，属于正确性而非功能。
- 需要产品层面的决定：账号功能是**降级为占位**（在文档与后台文案里写明当前不影响任何输出，
  避免管理员以为配了账号有用），还是**保留现状**。

### 实测发现：**酷我搜热门歌手会返回空列表**（预筛正确，但后果严重）（2026-09-19）

顺着「只先看搜索」往下查时发现的另一个问题。`kuwo.client.ts` 的搜索会
`raw.filter((song) => song.playable !== false)`，而 `playable` 取自
`payInfo.listen_fragment !== "1"`。用户搜「周杰伦」时客户端显示**「没有找到相关歌曲」**。

**先验证预筛有没有误杀**（3 个关键词、60 条样本，逐首真去走档位阶梯取地址）：

| listen_fragment | 样本数 | 能取到地址 |
| --- | --- | --- |
| `"1"`（被滤掉） | 54 | **0 条（0%）** |
| `"0"`（保留） | 6 | **6 条（100%）** |

**结论：预筛是准的，没有误杀。** `listen_fragment="1"` 的歌确实一条都取不到播放地址。

**又追加了一轮「换入口能不能救回来」的验证** —— 因为 `attemptLadder` 只试 `KUWO_TIERS`
的三档（`mp3/320k`、`mp3/128k`、`aac/48kaac`），**从没试过 `flac` / `zp` / `mgg` / `ogg`**，
而实测已知 `format=flac` 能拿到 mp3 320k、`zp` 能拿到真 FLAC。
如果被滤掉的歌能用这些入口取到，那预筛就是在丢**可播**的歌。

| 入口 | 命中 / 被滤掉的 40 首 |
| --- | --- |
| `mp3/320k` · `mp3/128k` · `aac/48kaac`（现用三档） | 0 / 40 · 0 / 40 · 0 / 40 |
| `flac/2000` · `flac/320k` | 0 / 40 · 0 / 40 |
| `zp/20000` · `al/2000`（真 FLAC 档） | 0 / 40 · 0 / 40 |
| `mgg/24000`（母带） · `ogg/300` | 0 / 40 · 0 / 40 |

**360 次尝试全部取不到地址** —— 预筛的结论彻底站得住，没有任何可播的歌被丢掉。
「换入口救回来」这条假设被排除，可以放心不再往这个方向查。

**但后果很严重** —— 逐关键词看：

| 关键词 | 上游返回 | `listen_fragment=1` | `=0` | 客户端最终显示 |
| --- | --- | --- | --- | --- |
| 周杰伦 | 20 条 | **20 条** | 0 条 | **空列表 →「没有找到相关歌曲」** |
| 经典老歌 | 20 条 | **20 条** | 0 条 | **空列表** |
| 陈奕迅 | 20 条 | 14 条 | 6 条 | 6 条 |

即：**搜热门歌手时酷我这条链路整体是空的**。上游明明返回 20 条，被预筛全部滤掉，
客户端拿到的是 0 条。而且这**与账号无关** —— 上面已证 `listen_fragment` 不随账号变化，
所以配 VIP 号也不会把这些歌「解锁」回来。

这不是实现 bug（预筛本身是对的），是**设计取舍的代价**：预筛的目的是「不列出点不开的歌」，
代价是「点不开的歌多的时候，列表直接空掉」。需要产品层面决定怎么处理，可选方向：

1. **空列表时给专属文案** —— 区分「上游没搜到」与「搜到了但都不可播」，
   后者提示「该音源下这些歌需要会员，可换 QQ 音乐 / 网易云试试」。
   改动最小（客户端文案），但需要服务端在 `meta` 里带回被滤掉的条数。
2. **列出但置灰** —— 保留歌名、标记「会员专享」，点击时明确提示不可播。
   体验最好，但要动客户端渲染与「可播」语义，属于契约变更。
3. **酷我返回空时自动兜底聚合结果** —— 语义上容易让人误解「酷我搜到了 QQ 的歌」，不推荐。
4. **保持现状** —— 只在文档里记着。

⚠️ 注意 `SearchService` 的 `meta.dropped` 目前**恒为 0**（注释说明「不再逐首探测，
也就不再丢歌」）—— 但酷我这条链路在**适配器内部**丢了歌，上层看不到。
要做方向 1 就得把这个数从适配器透出来。

### 重构：让「丢歌」从适配器里透出来（2026-09-19）

用户要求「重构一下后端的搜索」，并猜测「是多传了什么」。先把猜测证伪，再改真正的问题。

**请求头消融测试**（同一关键词、同一 URL，逐项去掉请求头比较响应）：

| 去掉的头 | 结果 |
| --- | --- |
| `uid` · `token` | **响应一个字节都不变** |
| `sign` | 不变（签名确实不校验） |
| `appid` · `api-ver` | 不变 |
| `ts` · `nc`（随机数） | 不变 |
| `User-Agent` | 不变 |
| **`Origin`** | **402**（msg 为空） |
| **`Referer`** | **402**（msg 为空） |

即：**我们每次搜索都多传了 `uid` / `token`（还有 `sign`、`appid`、`api-ver`、`ts`、`nc`），
而上游根本不读它们**；真正必需的只有 `Origin` 与 `Referer`。
所以「登录和没登录一样」**不是传错了什么**，是上游这个复刻接口没有账号维度 ——
与 `server/bodian/index.ts` 参考实现逐字段比对也确认请求形状完全一致，不是我们改坏的。

**真正的问题在别处**：`KuwoClient.searchSongs` 在**适配器内部**静默丢歌，
上层完全看不到。`SearchService` 的 `meta.dropped` 被硬编码成 `0`，
注释还写着「不再逐首探测，也就不再丢歌」—— 而酷我明明丢了 20 条。

**改动**：

| 文件 | 改动 |
| --- | --- |
| `upstream/tencent.client.ts` | `SearchResult` 加必填字段 `dropped: number`，附说明 |
| `upstream/tencent.client.ts` · `netease.client.ts` | 不做预筛，`dropped: 0` |
| `upstream/kuwo.client.ts` | `dropped: raw.length - list.length`，即被预筛滤掉的条数 |
| `music/search.service.ts` | `meta.dropped` 改为真实求和；新增 `meta.droppedBySource` |

`droppedBySource` 是必要的：聚合搜索（`source=all`）下「总共丢了 20 条」说明不了是哪家丢的，
而客户端要据此提示「这个音源下这些歌需要会员，换一个试试」。
单音源搜索时 `droppedBySource` 只有丢歌的那一家。

**同时修掉了三处会撒谎的注释与文案**（契约脚本测不出这类问题，但管理员会照着它做判断）：

- `kuwo.client.ts` 类注释原文写「后台的音源账号是**真正生效**的：登录成功即影响播放」→
  已改为「目前不影响任何输出」，并写明凭据唯一被读取的是 `uid` 的形状。
- `resolveLink` 注释原文写「账号的权益直接决定能不能拿到更高档」→ 已改为
  「凭据本身不改变拿到的档位」，唯一起作用的是 `uid` 形状。
- 后台 `MusicSourceManager.vue` 的告示原文标题是「**本页配置会直接影响播放**」→
  已改为「本页配置目前不影响播放结果」，并说明「测试通过 ≠ 凭据被识别」。

**验收**：`tsc --noEmit` 干净；契约 **251 项全绿**（249 + 新增 2 项），`Mapped` 路由 **113**；
`dist/` 重建（113 个文件，732667 → 408195 字节），`dist/public` 已重建。
新增的两项断言是「`meta.dropped > 0`（搜「周杰伦」）」与
「`meta.droppedBySource` 指出丢歌的是哪家音源」—— 前者依赖上游曲库，已在断言注释里写明。

> 📌 **注意这轮重构不改变客户端看到的内容**：被滤掉的歌仍然不下发（预筛本身是对的），
> 变的只是**丢了多少条现在能被上层看见**。要做「专属空态文案」还得客户端配合读 `dropped`。

### 后续修复：登录成功却按匿名播放 —— `upsertByLogin` 不重置 `enabled`

用户报「发码成功了，但搜索好像还是没有使用账号」。逐段核对搜索链路后确认
**链路本身没有问题**（见下），但查出一个会让它**看起来**完全没生效的缺陷。

**缺陷**：`music_source_account.repository.ts` 的 `upsertByLogin()` 里，
`DO UPDATE SET` 只刷 `token` / `phone` / `label` / `last_status` 等，
**唯独没有 `enabled`**。于是当 `(source, uid)` 上已经存在一条**未启用**的行时
（例如管理员先手工建了个占位账号、或曾把旧账号停用过），短信登录会：

- 覆盖成新 token、`last_status = 'ok'`、`last_checked_at` 刷新 → **后台显示登录成功**
- 但 `enabled` 保持 0 → `credentialFor()` 的 `WHERE enabled = 1 AND token <> ''` 取不到它
- 播放链路读到 `undefined`，**按匿名走**

结果就是最难查的一种表现：**每一步都显示成功，但账号完全没被使用。**

**修法**：`DO UPDATE SET` 补上 `enabled = 1`。管理员刚刚亲自走完短信登录，
意图足够明确，这里重新启用符合预期。（`create()` 本来就默认 `enabled = 1`，
只有「同一 uid 已存在且被停用」这一条路径会踩到。）

**验收**：`tsc --noEmit` 干净；契约 **249 项全绿**，`Mapped` 路由 **113**；
`dist/` 已重建（113 个文件，728902 → 407993 字节），产物里可见 `enabled = 1`。

### 「搜索没用上账号」的排查结论：链路是通的

> ⚠️ **先读上面那节。** 本节证明的是「凭据确实被送进了搜索请求」（链路无断点），
> 但 2026-09-19 的实测进一步确认：**上游对搜索请求里的凭据完全无反应，
> 真实 VIP 凭据的结果也与匿名逐字段相同**。所以「链路是通的」不等于「账号有用」——
> 这两件事在本项目里是分开的，别把本节当成「配了账号就该有变化」的依据。

**先说结论：搜索确实会带上后台配置的账号，用探针走真实代码路径（`KuwoClient.searchSongs`）
打印请求头可以证实 ——**

```
[1] 配了账号，搜索：uid=12345678  token=probe-token-not-real  <- /api/search/music/list?pn=1&rn=5&keyword=七里香
[2] 没配账号，搜索：uid=(空)      token=(空)                    <- 同上
```

逐段核对无断点：安卓 `search(source = searchSource)` → `searchSourceOf`（`kuwo` 不会被
降级成 `all`）→ `SearchService.stream` → `registry.of("kuwo")` → `searchSongs()` →
`clientOf()` → `credential()` → `signedGet` → `baseHeaders()`（`uid` / `token` 两个头）。

同时排除了三个可能被误当成原因的因素：

1. **聚合范围**：`AGGREGATED_SOURCES` 里确实**没有酷我**，但用户明确是选中「酷我」搜的，
   不是「全部」，所以这条不适用。（已在 `music-source.client.ts` 补上原缺失的注释。）
2. **有分支绕过凭据**：全项目 `new BodianClient()` 只有 4 处 —— `probeCredential`（显式传入
   待测凭据）、`sendSms` / `loginSms`（本来就不需要凭据）、`clientOf`（唯一入口）。
   **没有绕过凭据的分支。**
3. **客户端缓存**：安卓端搜索不做本地缓存（全项目只有 `TencentMusicApi.kt` 引用搜索接口，
   Room 里没有搜索结果表），所以「登录后搜同一关键词仍看到旧结果」不成立。

⚠️ **但「结果看起来一样」本身不能当成 bug 的证据。** 搜索结果的差异只来自
`kuwo.client.ts` 的 `raw.filter((song) => song.playable !== false)`，而 `playable`
取上游的 `payInfo.listen_fragment !== "1"`。这个字段**只对带权益的账号（VIP / 已购）**
才可能变化；普通账号下匿名与带凭据的结果**本来就应该逐条相同**
（历史实测 14/14 接口一致，样本就是一个普通账号）。另外 `token` 的取值被上游彻底忽略，
只有 `uid` 会被解析 —— 所以「带账号」在搜索上的可见收益本来就有限，
**主要收益体现在取址 / 播放的档位**上。

**给用户的判定方法**（不依赖肉眼比对结果）：

- 后台「音源账号」页签里，确认那一行的**「启用」开关是打开的**。这一列若为关，
  就是上面那个 `enabled` 缺陷的表现，已修。
- 点该行的「测试」：返回的 note 形如 `mp3 320kbps`；**若以「匿名」开头，说明这条记录的
  token 是空的**（`probeCredential` 对空 token 会加前缀），凭据根本没存进去。
- 想确认「账号是否真的影响了播放」，看的是**取址结果的码率**，不是搜索结果条数。

### 本轮新增的关键实测结论

1. **`listen_fragment` 的预测能力被证实**：累计 91 条样本（多组关键词 × 每首 5 个档位）零误判。
   凡 `"1"` 的拿不到地址，其余全部拿到。搜索阶段预筛可以放心用。
   **2026-09-19 追加验证**：被滤掉的 40 首歌再拿 **9 个入口**（含现用三档之外的
   `flac` / `zp` / `al` / `mgg` / `ogg`）逐个试，**360 次尝试全部取不到地址** ——
   「是不是我们太早放弃、换入口能救回来」这条假设被排除。
   ⚠️ 但预筛正确的代价见「酷我搜热门歌手会返回空列表」一节：**搜热门歌手时列表会整体空掉**。
2. **`uid` 必须是纯数字**（这条推翻了原先的结论，见下方修订记录）。传非数字 uid 时
   上游**拒绝下发任何播放地址**，而搜索、单曲信息、歌词全部照常 —— 「搜得到、放不出」。
   **`token` 的取值与取址无关**：乱码 token 配数字 uid 照样能取到地址，和匿名完全一样。
   因此 `resolveLink` 的匿名兜底**救不了非数字 uid**（匿名同样拿不到），最终还是 502。
   连通性测试**故意不退回匿名**（测试的职责就是把问题暴露出来）。
   **这条已落成写入校验**（用户拍板）：`numericUidOnly` 能力标记 + `assertUidShape`，
   在 `create` / `update` / `login` 三处拦掉非数字 uid（4007），存不进库。
   理由是上游的形状错误**是静默的** —— 存进去就是个要到播放时才暴露的坏账号。
3. **音频主机有四个**：`bd-er` / `bd-lv` / `bd-lw` / `bd-bj`，全部支持 https + Range。
   只写常见的那两个会挡掉约三分之一的请求，且表现为「有的歌能放、有的放不了」。
4. **档位降级方向反直觉，且现用的「320k」是虚标**（2026-09-18 五首样本实测）：

   | 请求 | 实际拿到 |
   | --- | --- |
   | `mp3` + `br=320k`（`320`/`320kbps`/`320000`/`320K` 全一样） | **mp3 128k** |
   | `mp3` + `br=128k` | mp3 128k |
   | `flac` + 任意 `br` | **mp3 320k**（4/5 首 320~324k） |
   | `zp` + `20000`（`al` + `2000` 等价） | **真 FLAC**（4/5 首 727~1702kbps） |

   **所以 `KUWO_TIERS` 的 `{format:"mp3", br:"320k", label:"高品质"}` 恒为 128k** ——
   客户端显示「高品质 320k」标签，且 `size` 按 320k 估算、下载前大小预估**虚报约 2.5 倍**。
   想要真 320k 得改请求 `format=flac`。样本里有一首歌三档全部只给 129k，
   所以音质必须按响应的 `format`/`bitrate` 回填。

   **匿名就能拿到全部档位**，账号凭据在音质上**零增益**：同歌同档位下匿名与真实凭据
   返回的文件**逐字节相同**（5/5 首）。所以账号体系的价值是「为上游将来收紧匿名访问
   预留通道」，而不是当下必需。`KUWO_TIERS` 里目前**没有**无损档。
5. **短信验证码登录已端到端跑通**（真实手机号 + 真实短信）。协议要点：
   - 传输是**明文 JSON**，**不要套 `{data, encrypt, method}` 信封** —— 套信封一律回
     HTTP 500 + `{"code":-1,"msg":"Service error"}`，**看起来像上游故障，实际是请求形状不对**。
   - `authType` 短信登录 = **`9`**。实测映射：1 手机号验证码（另一条流程，11004）、
     2 QQ（11008）、3/6/8 参数错误（-10）、4 账号密码（11027）、5 检查登录状态（11012）、
     7 Apple（11010）、9 短信验证码登录（200）、10 二维码（11052）。
     传错极具误导性：`authType: 2` 回「QQ授权失败」，像账号被风控。
   - 响应里 uid 字段是 **`data.id`，不是 `data.uid`**。
   - 发码参数名是 `encvMobile`（不是 `phone`），`type=2`。
   - 验证码在有效期内**可重复使用**。
   - 反汇编里 `_loginByVy` 的 `movz x16, #0x2` 存的是 Smi 编码，按字面量读会得出
     「authType = 1 或 2」，**两个都不对**。**参数取值逐个打出来，别从反汇编猜。**

### 修订记录

| 原结论 | 现状 | 原因 |
| --- | --- | --- |
| 「一份无效凭据比不带凭据更糟」（第 2 条） | **误诊，已推翻** | 当时对照用的是「乱码 token + 非数字 uid」，两个变量混在一起。拆开之后看清是 **uid 形状**在起作用，与 token 无关。**做上游对照必须一次只改一个变量。** |
| 「凭据必须成对有效或完全不带」（第 3 条） | **不成立** | 同上。token 给什么值都不影响取址。 |
| 「音质只有一个档次，`zp` 会被降级成 128k」（结论摘要第 2 条） | **部分错误** | 当年请求的是 `format=flac&br=flac`，那个确实被降级。正确参数 `format=zp&br=20000` 能拿到真 FLAC。 |

## 结论摘要

传输层**已经跑通**，但**不能直接接**。实测结论：

1. **搜索、音频直链、逐字歌词、封面全部可用**，无需登录。签名算法（`kuwotest` 盐 + URL 骨架 md5）复刻正确。
2. **音质：无损其实免费，但要用对参数**（原结论已修订，见「修订记录」）。未登录状态下
   请求 `320k` 会被**静默降级**成 128k mp3；请求 `format=flac&br=flac` 会被降级成 mp3 320k。
   但 `format=zp&br=20000` 能拿到**真 FLAC**，且**匿名就能拿**。
   所以项目现有的 0–18 音质档位模型对酷我需要重新映射，而不是「无意义」。
3. **正版热门曲大量不可播**。`七里香`(94237)、`告白气球`(7149583)、`兰亭序`(440616) 等一律返回 `code 20012 歌曲已下线`；能播的多是伴奏、Remix、翻唱和网友改编。搜「稻香」首屏是 `稻香 (原版伴奏)`、`稻香 (Remix摇滚版)`。
4. **歌词有编码缺陷**。LRCX 是 **GBK** 编码，现有实现按 UTF-8 解，中文全部变成 `\uFFFD`。
5. **架构上有一个硬阻塞**。现有「多音源」是 3 处 `source === "netease" ? netease : tencent` 三元表达式硬编码的，**默认分支是 QQ**。直接加第三个源，所有未改到的三元都会把酷我 ID 发给 QQ 上游，且不会报错。

所以接入的正确顺序是：**先修传输层缺陷 → 再抽音源分派 → 最后才接酷我**。

## 接入前必须修的缺陷

都在 `server/bodian/index.ts`，**属于传输层自身的 bug，与接入方式无关**：

1. **LRCX 编码**（`getLrcxLyrics`，L380-381）：`xorDecode` 之后必须按 **GBK** 解码。当前 `.toString('utf-8')` 让所有中文歌词变成乱码。服务端已有 `iconv-lite` 可用。
2. **参数未编码**（`signedGet`，L152-156）：`${k}=${v}` 直接拼接。关键字含 `&` 会切坏 query 并**静默返回别的歌**（实测传「A & B 测试」返回 3 条无关结果，不报错）；含空格/中文时签名基于未编码串、实际发送的是编码后 URL，签名可能对不上。应改用 `URLSearchParams` 并让签名与实际发送的 URL 一致。
3. **下载文件名清洗**（`downloadSong`，L468）：`[^a-zA-Z0-9 -_.]` 会把中文歌名全替换成 `_`，`晴天 - 周杰伦.flac` → `__ - __.flac`，大量歌曲互相覆盖。应只过滤 `\/:*?"<>|` 等非法字符。
4. **流与容错**（`download`，L438-457）：不处理背压、`end()` 不 await、异常分支泄漏 fd、不创建目标目录。
5. **无超时**：所有 `fetch` 都没有 timeout，上游挂起会永久阻塞。

另外 `server/bodian/index.ts` **不在 `server/tsconfig.json` 的 `include`（`src/**/*.ts`）里**，不会被 `tsc` 编译，目前是游离代码。接入时必须挪进 `server/src/`。

## 现有音源抽象的瓶颈

`UpstreamModule` 只注册了两个 provider，而「选哪个上游」的逻辑散落在 3 个地方，全部是硬编码三元表达式：

```
server/src/music/search.service.ts:46     itemSource === "netease" ? this.netease : this.upstream
server/src/music/stream.service.ts:79     source === "netease" ? this.netease : this.upstream
server/src/music/music.controller.ts:89   if (selectedSource === "netease") { … }
music.controller.ts:185 / 247             source === "netease" ? … : …
server/src/shares/song-share.service.ts:39 / 148 / 199
```

两个客户端也**没有共同接口**，签名还不一致：`NeteaseClient.requestLyric(id)` 收的是 `number`，`TencentClient.requestLyric(key)` 收的是 `{id, mid}`；`resolveLink` 一个 2 参一个 4 参。

后果很具体：`music.controller.ts:299` 的 `sourceOf()` 一旦放行 `"kuwo"`，`link` / `info` / `lyrics` 三个端点都会落到 `else` 分支，**把酷我 ID 当成 QQ ID 发出去**。`sourceOf` 的默认值也正是 `"tencent"`。这类错误不报错、不进日志，只表现为「这首歌没声音」。

`playlists.controller.ts:26` 的注释已经预判了这一点：

> 歌单项必须能被当前音乐路由解析；新增来源时先补齐 music 模块和双端客户端。

## 目标

- 把「选上游」从三元表达式收敛成一个注册表，新增音源只需注册一个 provider。
- 让 `BodianClient` 保持为纯传输层（签名、加密、解码），领域映射交给独立的适配器。
- 接入酷我后，QQ / 网易云的搜索、播放、歌词、收藏、歌单行为**完全不变**。
- 酷我音质按实际返回值如实上报，不虚标。
- 桌面端可显式选酷我；Android 的默认聚合搜索行为需要先决策。

## 非目标

- 不改 `StreamService.proxy` 的转发实现（酷我直链单主机、支持 Range，现有实现可直接复用）。
- 不重构客户端 `source` 的传递方式 —— 客户端已把它当**不透明字符串**（`source.ifBlank { "tencent" }`、`"$source:$id"` 复合键），不需要改成枚举。
- 不为酷我实现音质选择器。它只有一档，做了也是假的。
- 不引入短信登录。见「待决策」。

## 风险

- **内容质量**：接入后酷我带来的主要是伴奏、Remix、翻唱。如果产品预期是「补全 QQ 缺失的正版曲库」，实际收益可能远低于预期 —— 建议阶段 2 结束后先做一次人工抽样，再决定是否进聚合搜索。
- **静默降级**：酷我不报错、只降级。如果不按响应里的 `bitrate` 回填，客户端会把 128k 当无损存进下载记录。
- **默认分支陷阱**：阶段 1 若漏改任何一处三元，酷我会被当成 QQ。建议阶段 1 完成后 `grep '"netease"'` 复查一遍，确认只剩白名单校验和类型定义。
- **无超时**：阶段 0 若只修编码不修超时，上游挂起会拖住整个搜索（`Promise.allSettled` 要等最慢的那个）。
