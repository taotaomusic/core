# 多地区部署(只读副本读写分离)

[返回文档中心](README.md)

最后更新:2026-10-18

本页描述多地区部署的形态、读写路由的**实际规则**、熔断降级行为与**主库故障时的人工应对手册**。实现代码在 `src/database/`(database.service.ts、db-routing.* 四件套)。单机部署不需要读本页 —— 不配置 `DATABASE_REPLICA_URL` 时全部行为与从前逐字节一致。

## 1. 目标与形态

**目标**:用户分布在多个地区时,让**读请求**在本地完成(搜索、播放记录、歌单、列表页都是读),写请求跨区回到主库。不引入 Redis、不改客户端、不破坏任何现有接口契约。

**形态**:一个主地区 + 若干镜像地区,每个地区一台应用实例 + 一个**物理流复制**的本地 PostgreSQL 只读副本(异步):

```text
        主地区                             镜像地区 B / C ...
  ┌─────────────────┐                 ┌─────────────────────────┐
  │ app 实例        │                 │ app 实例                │
  │  ├─ DATABASE_URL ──────┐          │  ├─ DATABASE_URL ────────────┐
  │  └─ (无副本)    │      │          │  └─ DATABASE_REPLICA_URL ──┐ │
  │                 v      │          │                            v │
  │  PostgreSQL 主库 <─────┼── 物理流复制 ──>  PostgreSQL 副本     │
  └─────────────────┘      │          └────────────────────────────┼─┘
                           │                                       │
                           └──────── 写请求按需跨区回到主库 ────────┘
```

- 写请求(含所有事务)始终打在**主库**上,但可以由当地的 app 实例发起 —— 写后的内存态(会话、缓存)与发起实例自洽。
- 读请求默认打**本地副本**,同步延迟由 PostgreSQL 流复制决定(通常是毫秒级)。
- **IM 只接一个地区**:非主地区必须设 `IM_ENABLED=false`(IM 的 Gateway 地址与设备会话是全局单点,不随副本走)。
- 各地区的 `AUTH_SECRET` 与 `CRYPTO_PSK_HEX` **必须完全一致**:令牌与传输加密会话是跨地区通用的,不一致会让用户在地区间"随机掉登录"或握手失败。

> 这不是高可用(HA):主库仍是单点,没有自动选主。主库故障时的行为与人工恢复流程见 §5。

## 2. 读写路由规则

路由判定在**每个查询**上执行,优先序从高到低(实现见 `DatabaseService.resolveTarget`):

| 序 | 判定 | 结果 |
| --- | --- | --- |
| 1 | 查询级显式 pin(第三参 `{ primary: true }`) | 主库 |
| 2 | 未配置 `DATABASE_REPLICA_URL` | 主库(等于单机形态) |
| 3 | 写请求方法:POST / PUT / PATCH / DELETE | 主库 |
| 4 | 管理端路径 `/api/v1/admin/*`、`/api/v1/app/admin/*`(读也走主库) | 主库 |
| 5 | 该用户处于「写后立读」窗口(2 秒,见下) | 主库 |
| 6 | SQL 首词是写语句(安全网) | 主库 + 节流告警 |
| 7 | 其余 | 本地副本 |

**无路由上下文时(启动期、定时任务、CLI 工具)一律走主库** —— 安全默认,宁可多走主库也不让写后的读落到延迟未知的副本上。

### 写后立读(2 秒窗口)

物理复制是异步的,「写主库、读副本」之间天然有延迟。写请求**成功返回后**,该用户 ID 会进入 2 秒窗口(`db-write-activity.tracker.ts`),窗口内该用户**所有**读请求升级到主库,覆盖「注册后立即鉴权」「收藏后立即刷新」「改资料后立即回显」这类时序。

- 标记点:全局写拦截器(登录用户的所有写请求)+ 注册/登录控制器手动标记(公开路由没有 `request.user`)。
- 窗口是进程内状态,重启清空;多实例/多地区下各实例各算各的(每地区单实例部署下自洽,扩容假设见 [11-architecture-modules.md](11-architecture-modules.md) §4)。
- 令牌解析只取 `sub`,**不验签**;解析失败(管理端不透明令牌等)按不在窗口处理 —— 伪造 `sub` 的后果最多是多走一次主库读,不构成越权。

### 显式 pin 清单(读上下文里的写)

有些写藏在 GET 请求里(路由规则 3 覆盖不到),下表是全部已知点。**新增此类路径时必须同样 pin**,否则安全网会在日志里告警(见 §6),长期靠安全网兜底会失去性能意义:

| 位置 | 语句 | 原因 |
| --- | --- | --- |
| `open-api/open-api-key.repository.ts` `touchLastUsed` | UPDATE | 开放 API 鉴权时刷新最近使用时间 |
| `shares/song-share.repository.ts` `noteAccess` | UPDATE | 分享页每次打开累加访问计数 |
| `shares/song-share.service.ts` `requiredShare` | 副本未命中时回主库重查 | 分享页匿名消费,写后立读窗口覆盖不到「刚创建就打开」 |
| `playlists/playlists-cover.service.ts` `doFetchAndStore` | UPDATE | 读取路径上的封面惰性回源自愈 |
| `auth/users.repository.ts` `ensureImUid` | UPDATE + 紧随的回读 | IM 设备端触发,无用户令牌,窗口覆盖不到 |
| `image-generation/image-task.repository.ts` `updateResult` | UPDATE | 轮询任务详情时顺路更新状态 |
| `auth/auth.controller.ts` register/login | 手动标记窗口 | 公开路由没有 `request.user` |

安全网兜底的逻辑:`first()` 既执行 SELECT 也承接 `INSERT ... RETURNING`,单看方法名无法判断读写,所以按 **SQL 首词**判断(INSERT/UPDATE/DELETE/… 以及 `WITH` 开头、`SELECT ... FOR UPDATE` 一律视为写)。命中且本应走副本时自动改走主库,并打一条节流 WARN。

## 3. 熔断与降级

| 场景 | 行为 |
| --- | --- |
| 副本单次连接失败 | 本次查询立即回退主库,计数 +1,打 WARN |
| 副本回放冲突(SQLSTATE 40001 `conflict with recovery`) | 本次查询立即回退主库,**不计降级**,打节流 WARN(5 分钟一条) |
| 副本连续 3 次连接失败 | **降级 30 秒**:全部读直连主库,窗口过期后再试副本 |
| 主库连续 3 次连接失败 | **熔断 15 秒**:窗口内写请求立即返回 `503/5033`,不等连接超时 |
| 熔断窗口过期 | 放行试探;仍失败则重新熔断。健康读请求全程不受影响(走副本) |

只有**连接类失败**(SQLSTATE 08 类、ECONNREFUSED/ETIMEDOUT、pg-pool 连接超时等)才计数;语法错误、约束冲突等业务性失败不会触发熔断 —— 否则一段写错的 SQL 就能把主库「熔断」掉。详情可看 `database.service.ts` 的 `isConnectivityError`。副本回放冲突(40001)是副本独有形态:本次查询回退主库重试,但同样不计降级。

### 健康检查语义

`/health` 由 `DatabaseService.ping()` 驱动,有三种结果:

| 状态 | 触发条件 | HTTP |
| --- | --- | --- |
| `{"status":"up"}` | 主库可用(副本是否可用不影响,副本挂了只是降级直连) | 200 |
| `{"status":"degraded"}` | 主库不可用但副本还能读 —— 读服务仍在,进程不应被摘除,但要告警人工介入 | 200 |
| `502/5020`(抛错) | 主库与副本都不可用 | 502 |

运维编排/拨测应把 `degraded` 当**告警**而不是故障摘除信号。CI 的契约验证轮询的是 `"up"`(单机形态恒满足)。

## 4. 部署第二地区(步骤)

1. **主库侧**准备复制账号(PG18 默认 `wal_level=replica`,无需改),`pg_hba.conf` 放行副本地区来源:
   ```sql
   CREATE ROLE replicator WITH REPLICATION LOGIN PASSWORD '强密码';
   ```
2. **副本地区**用 `pg_basebackup` 初始化数据目录(会写好 `primary_conninfo`):
   ```bash
   pg_basebackup -h 主库地址 -U replicator -D /var/lib/postgresql/data -Fp -Xs -P -R
   ```
   `-R` 写入的 `standby.signal` + `primary_conninfo` 使实例以热备(只读)模式启动,无需手工改配置。
3. **副本地区 app** 增加配置(其余与单机部署相同):
   ```env
   DATABASE_URL=postgres://...@主库地址:5432/music        # 写请求用它
   DATABASE_REPLICA_URL=postgres://...@127.0.0.1:5432/music  # 读请求走本地副本
   IM_ENABLED=false                                       # IM 只接主地区
   AUTH_SECRET=与主地区完全一致
   CRYPTO_PSK_HEX=与主地区完全一致
   ```
4. **验证**:
   - 主库 `SELECT * FROM pg_stat_replication;` 能看到副本且 `state=streaming`;副本 `SELECT pg_is_in_recovery();` 返回 `t`;
   - 副本地区 `/health` 返回 `"up"`;
   - 冒烟:该地区登录(写走主库)→ 立即拉歌单列表(写后立读窗口内走主库)→ 稍后列表(走副本)。
5. **Docker Compose 部署**注意:compose 文件里 `DATABASE_REPLICA_URL` 已在 app 服务透传;URL 主机名要写容器内可达地址(如 `host.docker.internal`),不能沿用 `db`(那是本机主库服务名)。

## 5. 主库故障与人工切换手册

**本方案不做自动 failover**:异步复制 + 自动选主有脑裂与丢数据双重风险,当前规模(单主写入)人工处置足够。故障处置:

1. **确认**:各镜像地区 `/health` 变 `degraded`;日志出现「主库连续连接失败,熔断」;写操作报 `503/5033`。
2. **等待(首选)**:主库是进程/网络抖动时,恢复后路由自动恢复(熔断窗口过期即放行),副本自动追平,无需任何操作。
3. **提升副本(主库短期修不好时)**:
   1. 选一个数据最新的副本地区(`SELECT pg_last_wal_receive_lsn()` 对比),在副本上执行 `SELECT pg_promote();`(或 `pg_ctl promote`),确认 `pg_is_in_recovery()` 返回 `f`;
   2. 把**所有地区**的 `DATABASE_URL` 指到新主库(建议用稳定的域名/DNS 记录,避免到处改 IP),被提升地区删掉或改掉 `DATABASE_REPLICA_URL`;
   3. 各地重启应用后 `/health` 应回到 `up`;
   4. **旧主库恢复后绝不能直接起服务**:先按 §4 重新 `pg_basebackup` 重建为副本,否则两个主库同时可写会造成分叉(脑裂)。任何情况下先确认旧主库已停写再提升。
4. **数据损失评估**:异步复制意味着故障瞬间未同步的写(通常毫秒级,繁忙时可能更多)会丢失。该窗口大小 = 副本 `pg_last_wal_replay_lsn` 与主库最后写入的差距,切换前用命令记录一次。

## 6. 监控与日志关键词

| 关键词 | 含义 | 处理 |
| --- | --- | --- |
| `只读副本连续连接失败，降级为直连主库` | 副本 30 秒降级已触发 | 查副本进程/网络;不修也会一直直连主库,读延迟变大 |
| `主库连续连接失败，熔断` | 写了 15 秒熔断窗口 | 按 §5 处置;若只是抖动可观察 |
| `读上下文检测到写语句，已自动改走主库` | 有仓库漏标 pin,安全网兜住了 | 按日志里的 SQL 指纹补 `{ primary: true }`(见 §2 pin 清单) |
| `只读副本查询失败（1/3）` | 副本单次失败已回退主库 | 偶发可忽略,持续出现按降级处理 |
| `只读副本回放冲突（40001）` | 该查询被副本回放取消,已回退主库重试(不计降级) | 偶发可忽略;频繁出现说明主库写入压力大,可调大副本的 `max_standby_streaming_delay` |

## 7. 边界与已知限制

- **写路径没有加速**:写请求跨区到主库执行,延迟 = 地区间网络延迟。这是数据一致性的必要代价;IM 只在主地区也是同理。
- **副本不替代备份**:物理副本会同步 `DROP TABLE`。主库仍须按 [44-database-operations.md](44-database-operations.md) 的口径做定时 `pg_dump` 备份。
- **连接池容量翻倍**:主库池与副本池各 10 连接(常量写在 `database.service.ts`),部署前确认 PostgreSQL `max_connections` 与各地区实例数的乘积有富余。
- **管理端一律走主库**(路径前缀 pin):管理流量小、时序敏感(登录后立即读会话资料),不做读写分离。
- **本方案不改客户端**:全部路由在服务端完成,接口契约、加密链路、分享播放器均不受影响;契约验证(`tools/verify-contract.mjs`)在单机形态下行为不变。

## 8. CI 里的副本路径验证(2026-10-18 起)

根 CI 的 `server` job 连跑**两遍契约**(见 [22-contract-verification.md](22-contract-verification.md) §7):

1. **单机形态**第一遍(不配副本)—— 保住单机部署的逐字节等价性;
2. **副本路径**第二遍 —— 把验证库自己兼作「只读副本」(`DATABASE_REPLICA_URL` 指向同一实例)重启后重跑全量契约,并过两道门禁:
   - 启动日志出现「已配置只读副本」:证明双池路由真实启用,而不是静默退化;
   - 「读上下文检测到写语句」零告警:**契约触达**的读路径上漏 pin 即 CI 红,把安全网(§2)从「生产日志告警」升级为「提交前门禁」;契约覆盖不到的读路径(IM 受 `IM_ENABLED` 开关、绘图任务、封面回源自愈等)仍只有运行时安全网兜底,这批位点的 pin 是否齐全要靠评审人肉确认(全部已知位点见 §2 pin 清单)。

> 自指副本验证的是**路由与连接池接线**,不是复制延迟 —— 延迟与写后立读的真实效果需要两套实例 + 真实流复制,CI 不搭,上线前按 §4 第 4 步冒烟。副本故障降级路径(§3)暂未纳入门禁,后续可再加一遍指向不可达端口的契约。
